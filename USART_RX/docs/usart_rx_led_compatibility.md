# USART 接收控制 LED 兼容性问题总结

## 1. 环境信息

- MCU：`STM32F103C8`
- 内核：`Cortex-M3`
- 外设库：`STM32 StdPeriph`
- 编译链：`Keil ARMCC5`
- 串口：`USART1`
- LED 引脚：`PC13`

## 2. 问题现象

串口监视器发送 `1` 时，LED 没有按预期点亮；发送 `0` 时，LED 也没有严格按“发 0 熄灭”的逻辑工作。

## 3. 根因分析

根因不是 GPIO 初始化错误，也不是 USART 基本初始化错误，而是“发送格式”和“代码比较方式”不一致。

- 串口监视器在文本模式下发送 `1`，实际发送的是 ASCII 字符 `'1'`，对应 `0x31`
- 串口监视器在文本模式下发送 `0`，实际发送的是 ASCII 字符 `'0'`，对应 `0x30`

原始代码如果按数值 `1`、`0` 去比较，就会出现下面的问题：

- `receiveData == 1` 比较的是 `0x01`
- 但串口实际收到的是 `0x31`
- 因此条件不成立

## 4. 现有证据

- `PC13` 低电平点亮、高电平熄灭，这一硬件逻辑是成立的
- `main.c` 中上电闪灯代码能工作，说明 LED 硬件链路正常
- 串口监视器界面显示发送的是文本 `"1"`、`"0"`
- 因此问题位于串口接收值的判定逻辑，而不是外设初始化本身

## 5. 风险点和边界条件

- 文本模式发送的是 ASCII 字符，不是原始字节
- 十六进制/原始字节模式下，可能发送的是 `0x01` 和 `0x00`
- 某些串口工具可能自动追加 `\r`、`\n` 或 `\r\n`
- `PC13` 为低电平点亮，逻辑不能写反

## 6. 兼容方案

接收逻辑同时兼容以下几种输入：

- 文本模式：`'1'`、`'0'`
- 原始字节模式：`0x01`、`0x00`
- 自动忽略：`\r`、`\n`
- 其他非法输入：保持当前 LED 状态不变

兼容处理代码如下：

```c
if ((receiveData == (uint8_t)'1') || (receiveData == (uint8_t)0x01))
{
    GPIO_WriteBit(GPIOC, GPIO_Pin_13, Bit_RESET);
}
else if ((receiveData == (uint8_t)'0') || (receiveData == (uint8_t)0x00))
{
    GPIO_WriteBit(GPIOC, GPIO_Pin_13, Bit_SET);
}
else if ((receiveData == (uint8_t)'\r') || (receiveData == (uint8_t)'\n'))
{
    /* 忽略串口工具附带的行尾字符 */
}
else
{
    /* 保持当前 LED 状态不变 */
}
```

## 7. 修改范围

本次只修改 `user/main.c` 中串口接收后的判断逻辑。

- 不改 GPIO 初始化
- 不改 USART 初始化
- 不改接口
- 不改文件结构
- 属于最小必要修改

## 8. 验证建议

1. 文本模式，不带行尾，发送 `1`
   - 预期：LED 点亮
2. 文本模式，不带行尾，发送 `0`
   - 预期：LED 熄灭
3. 文本模式，带 `CRLF`，发送 `1`、`0`
   - 预期：仍可正常控制
4. 十六进制模式，发送 `01`
   - 预期：LED 点亮
5. 十六进制模式，发送 `00`
   - 预期：LED 熄灭

## 9. 结论

本问题本质上是串口协议解释不一致导致的输入判定错误。当前兼容方案可以同时适配文本发送和原始字节发送，适合当前实验阶段使用。如果后续协议固定为单一格式，再进一步收敛判断逻辑会更合适。
